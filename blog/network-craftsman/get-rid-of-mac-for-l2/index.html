Pourquoi ne pas avoir un adressage L2 réellement utilisable pour les communications locales, et réserver L3 au routage inter-réseaux ?

Il y a une différence entre apprendre comment fonctionne un système et commencer à se demander pourquoi il fonctionne de cette manière.

C’est précisément cette transition qui m’a amené à cette réflexion.

Au départ, j’apprenais simplement les couches OSI, TCP/IP, les adresses MAC, les adresses IP, les switches, les routeurs, l’encapsulation et le routage. Puis, à force de suivre le trajet d’une simple requête à travers les différentes couches, une question a fini par apparaître :

Pourquoi avons-nous besoin d’un adressage IP jusque dans le réseau local alors que la couche 2 possède déjà son propre système d’adressage ?

Et derrière cette question, une idée plus radicale est apparue :

Pourquoi ne pas avoir un véritable réseau local L2, où les équipements communiqueraient directement par leurs adresses MAC, et réserver la couche 3 au seul rôle d’interconnexion entre réseaux ?

Je ne prétends pas avoir découvert une nouvelle architecture Internet. L’objectif de cette réflexion est beaucoup plus simple : partir des mécanismes fondamentaux que j’ai appris et pousser leur logique jusqu’à remettre en question l’architecture actuelle.

1. Tout a commencé par une distinction assez simple : L2 contre L3
#

En étudiant les réseaux, j’ai commencé par comprendre la différence fondamentale entre un switch et un routeur.

Un switch travaille principalement en couche 2.

Il manipule des trames Ethernet et prend ses décisions à partir des adresses MAC.

Sa logique peut être résumée ainsi :

Adresse MAC → Port physique

Il apprend progressivement quelles adresses MAC sont accessibles derrière quels ports et construit une table de commutation, souvent appelée table CAM.

Par exemple :

MAC                         PORT

AA:AA:AA:AA:AA:01           1
BB:BB:BB:BB:BB:02           2
CC:CC:CC:CC:CC:03           5

Lorsqu’une trame arrive :

Destination MAC = BB:BB:BB:BB:BB:02

le switch sait qu’il doit l’envoyer vers le port 2.

Le routeur fonctionne selon une logique différente.

Il ne cherche pas simplement une interface physique correspondant à une adresse MAC. Il travaille avec des adresses IP et une table de routage :

Destination IP → Interface / Next-Hop

Cette distinction m’a conduit à une première constatation :

Le switch s’occupe de la circulation locale tandis que le routeur s’occupe de l’interconnexion entre réseaux.

C’est d’ailleurs une distinction que j’avais déjà formalisée pendant mon apprentissage : la MAC est une adresse plate associée à l’interface réseau, tandis que l’IP apporte un adressage logique et hiérarchique permettant le routage entre réseaux.

2. Puis j’ai commencé à suivre une donnée au lieu de simplement apprendre les définitions
#

C’est probablement le moment où ma compréhension a réellement changé.

Plutôt que de mémoriser :

« TCP est la couche 4. IP est la couche 3. Ethernet est la couche 2. »

j’ai essayé de suivre une communication réelle.

Imaginons qu’un programme veuille envoyer des données.

L’application produit ses données.

TCP ajoute notamment les ports et les informations nécessaires à son fonctionnement.

IP ajoute :

IP source
IP destination
TTL
...

Puis Ethernet encapsule le paquet IP dans une trame :

MAC source
MAC destination
EtherType
----------------
Paquet IP
----------------
FCS

J’ai alors découvert une distinction fondamentale :

Le paquet IP n’est pas la trame Ethernet.

La trame est le conteneur L2.

Le paquet est le contenu L3.

On peut le représenter ainsi :

┌───────────────────────────────────────────────┐
│                Trame Ethernet                │
│                                               │
│  MAC src │ MAC dst │ IP │ TCP │ Données │ FCS│
│           └──────────────┬────────────────────┘
│                          │
│                     Paquet IP
└──────────────────────────┴────────────────────┘

Et surtout, la trame est locale.

Lorsqu’un paquet traverse un routeur, la trame Ethernet précédente disparaît et le paquet est ré-encapsulé dans une nouvelle trame adaptée au réseau suivant.

Cette distinction entre le paquet et son enveloppe est devenue essentielle dans ma compréhension du routage.

3. J’ai alors compris que la MAC est déjà un adressage local
#

C’est ici que mon raisonnement a commencé à diverger de la simple description du modèle TCP/IP.

Une interface réseau possède une adresse MAC.

Dans un réseau Ethernet, le switch peut utiliser cette adresse pour déterminer vers quelle interface transmettre une trame.

Donc, à l’intérieur d’un domaine Ethernet, nous avons déjà quelque chose qui ressemble fortement à un système d’adressage :

Machine A
MAC AA:AA:AA:AA:AA:01

        ↓

Switch

        ↓

Machine B
MAC BB:BB:BB:BB:BB:02

La question est alors devenue presque inévitable :

Si L2 sait déjà identifier les interfaces d’un réseau local, pourquoi devons-nous ajouter L3 à chaque machine ?

Pourquoi une machine du même réseau local doit-elle avoir :

MAC
+
IP

pour communiquer avec une autre machine qui se trouve à quelques mètres et derrière le même switch ?

4. C’est là que j’ai commencé à imaginer une autre architecture
#

J’ai volontairement essayé d’oublier, pendant quelques instants, la manière dont Internet est construit aujourd’hui.

Je me suis demandé :

Et si un LAN était réellement un réseau L2 ?

Quelque chose comme :

                 LAN
                  │
              ┌───┴───┐
              │ Switch│
              └───┬───┘
          ┌────────┼────────┐
          │        │        │
        PC-A     PC-B     Serveur
        MAC-A    MAC-B    MAC-C

Dans cette vision, les communications locales n’auraient pas besoin d’IP.

Une machine voudrait parler à une autre ?

Elle utiliserait directement son adresse L2.

MAC-A
  │
  │  Trame Ethernet
  ▼
Switch
  │
  ▼
MAC-B

Le switch resterait entièrement concentré sur sa fonction fondamentale :

MAC → PORT

Il n’aurait pas à se préoccuper de la logique IP.

5. Et L3 deviendrait alors véritablement une couche d’interconnexion
#

Dans cette architecture imaginaire, la couche 3 commencerait réellement à la frontière du réseau.

On aurait quelque chose comme :

             LAN A
        Communication L2
              │
              │
           [Routeur]
              │
              │ L3
              │
        ───── Internet ─────
              │
              │
           [Routeur]
              │
              │
             LAN B
        Communication L2

Le rôle du routeur serait alors très clair :

Sortir du réseau local.

À l’intérieur :

L2
MAC → MAC

À l’extérieur :

L3
Réseau → Réseau

Cela donnerait une séparation conceptuelle beaucoup plus nette :

L2 = communication locale

L3 = interconnexion de réseaux

Et c’est précisément cette séparation qui m’intéresse.

6. Pourquoi cette idée me paraît séduisante
#

Parce qu’elle donne l’impression d’éliminer une partie de la complexité.

Dans le modèle actuel, même une communication locale peut faire intervenir plusieurs mécanismes :

Application
    ↓
TCP/UDP
    ↓
IP
    ↓
ARP
    ↓
Ethernet
    ↓
Switch

Le protocole ARP existe notamment parce qu’il faut résoudre une correspondance entre :

IP
↓
MAC

Autrement dit, une machine connaît logiquement son correspondant par son adresse IP, mais elle doit finalement trouver son adresse L2 pour construire la trame.

J’ai commencé à me demander :

Pourquoi ne pas communiquer directement avec l’identifiant L2 lorsque le destinataire est local ?

Cela supprimerait conceptuellement une partie de cette traduction.

Le chemin local pourrait devenir :

Application
    ↓
Transport
    ↓
L2
    ↓
Physique

Tandis que le chemin vers un autre réseau serait :

Application
    ↓
Transport
    ↓
L3
    ↓
L2
    ↓
Physique

La couche 3 deviendrait alors réellement conditionnelle à la nécessité de quitter le réseau local.

7. Mais en poussant l’idée, j’ai aussi découvert pourquoi l’IP existe
#

C’est probablement le point le plus important de cette réflexion.

Une adresse MAC est pratique localement, mais elle n’est pas conçue pour effectuer du routage hiérarchique à grande échelle.

Elle est essentiellement plate.

Prenons :

AA:AA:AA:AA:AA:01

Cette adresse ne nous dit pas naturellement :

dans quel réseau se trouve l'équipement ;
dans quel sous-réseau il se trouve ;
par quel routeur il faut passer ;
quelle route résumée peut être utilisée.

L’IP, au contraire, permet une hiérarchie.

Par exemple :

192.168.10.0/24

peut représenter tout un réseau.

Un routeur n’a donc pas besoin de connaître individuellement chaque machine pour prendre une décision de routage.

C’est précisément l’une des raisons pour lesquelles l’adresse IP est indispensable à grande échelle : elle permet de structurer l’espace d’adressage et de rendre possible le routage hiérarchique.

Et c’est là que mon idée commence à rencontrer sa première vraie difficulté.

8. Une adresse MAC décrit une interface ; une IP décrit une position logique
#

Cette distinction m’a également obligé à abandonner une autre simplification.

Une machine n’a pas nécessairement une seule interface réseau.

Elle peut avoir :

Ethernet
Wi-Fi
VPN
Interface virtuelle
...

Et chacune peut avoir ses propres identifiants.

Cela signifie qu’il est plus juste de dire :

Une adresse MAC ou une adresse IP identifie une interface dans un contexte réseau donné, pas nécessairement une machine physique dans son ensemble.

Cette distinction devient particulièrement importante dès qu’on parle de routage, de virtualisation ou de mobilité.

9. Le problème de l’échelle
#

Mon architecture imaginaire fonctionne assez naturellement pour :

10 machines

Peut-être même :

1000 machines

Mais que se passe-t-il avec :

100 000 machines ?

Ou :

1 000 000 machines ?

Un système fondé uniquement sur des adresses plates devrait trouver un moyen de savoir où se trouve chaque destinataire.

L’adressage hiérarchique devient alors extrêmement précieux.

Avec IP, un routeur peut raisonner sur des préfixes :

10.0.0.0/8

plutôt que sur des millions d’adresses individuelles.

On retrouve donc une idée fondamentale :

L2 est excellent pour la proximité. L3 est excellent pour la structure.

Et peut-être que mon intuition initiale ne demande donc pas de supprimer L3 du LAN, mais de réfléchir à une séparation plus propre de leurs responsabilités.

10. Le problème de la mobilité
#

Imaginons maintenant une machine :

PC
MAC = AA:AA:AA:AA:AA:01

Elle quitte :

LAN A

et rejoint :

LAN B

Sa MAC peut rester exactement la même.

Mais sa position logique a changé.

Avec IP, on peut lui attribuer :

LAN A → 192.168.1.x

LAN B → 10.0.0.x

La hiérarchie IP permet donc de représenter son appartenance au nouveau réseau.

Avec un système uniquement fondé sur la MAC, il faudrait réintroduire ailleurs cette notion de localisation.

Et c’est probablement la leçon la plus intéressante de mon raisonnement :

Lorsque l’on retire un mécanisme, il faut vérifier si l’on ne recrée pas exactement le même mécanisme sous une autre forme.

11. Je ne cherche donc pas à supprimer l’IP
#

Après avoir poussé cette réflexion, ma position est devenue plus nuancée.

Je ne pense plus :

« L’IP est inutile dans un LAN. »

Je pense plutôt :

« Pourquoi ne pas exploiter davantage les capacités d’adressage et de communication de L2 pour les communications qui restent strictement locales, et réserver autant que possible la complexité de L3 aux communications qui franchissent réellement une frontière réseau ? »

Cette formulation est différente.

Elle ne cherche pas à remplacer IP.

Elle cherche à interroger la manière dont les différentes couches sont utilisées.

12. Le problème est peut-être moins l’existence de L3 que son omniprésence
#

L’architecture réseau moderne est le résultat de décennies d’évolution.

Elle doit fonctionner avec :

  • Ethernet ;
  • Wi-Fi ;
  • fibre ;
  • réseaux mobiles ;
  • VPN ;
  • datacenters ;
  • virtualisation ;
  • cloud ;
  • NAT ;
  • firewalls ;
  • tunnels ;
  • VLAN ;
  • routage dynamique ;
  • IPv4 ;
  • IPv6 ;
  • et une quantité considérable de matériel historique.

La complexité actuelle n’est donc pas nécessairement le résultat d’une mauvaise conception initiale.

Elle vient aussi du fait que le réseau doit rester :

compatible
scalable
interopérable
résilient
routable
sécurisable

à une échelle gigantesque.

C’est une contrainte très différente de celle d’un petit LAN domestique.

13. Et c’est probablement là que se trouve la vraie question
#

Ma question initiale était :

Pourquoi ne pas avoir un adressage L2 réellement utilisable pour les communications locales, et réserver L3 au routage inter-réseaux ?

Après avoir suivi le raisonnement jusqu’au bout, je pense que la question plus intéressante est :

Quelle serait l’architecture optimale si nous pouvions redessiner la frontière entre L2 et L3 aujourd’hui, sans être prisonniers de l’histoire d’Internet ?

Parce qu’une chose est désormais claire pour moi.

L2 et L3 ne sont pas simplement deux technologies concurrentes.

Elles répondent à deux problèmes différents.

             L2
              │
       « Qui est ici ? »
              │
              ▼
        Communication
           locale


             L3
              │
       « Où est ce réseau ? »
              │
              ▼
        Interconnexion
         de réseaux

La MAC répond très bien à la proximité.

L’IP répond très bien à la localisation logique et au routage.

14. Ce que cette réflexion m’a appris sur les réseaux
#

Paradoxalement, cette idée est née alors que j’étais encore en train d’apprendre les bases.

Je voulais comprendre :

OSI
TCP/IP
Ethernet
MAC
IP
ARP
Switch
Routeur
Encapsulation
NAT

Puis j’ai commencé à suivre réellement le parcours d’une donnée.

J’ai compris que :

L'application produit les données.

TCP/UDP organise le transport.

IP fournit l'adressage logique.

Ethernet fournit le transport local.

Le switch commute les trames.

Le routeur interconnecte les réseaux.

NAT peut traduire les identités à la frontière.

Et finalement, cette compréhension m’a conduit à poser une question qui n’était plus dans le cours :

Est-ce que cette architecture est nécessairement la meilleure architecture possible ?

Je n’ai pas encore de réponse définitive.

Et c’est précisément ce qui rend la question intéressante.

Conclusion
#

Apprendre les réseaux ne devrait peut-être pas s’arrêter à :

« Voici comment fonctionne un switch. »

ou :

« Voici comment fonctionne un routeur. »

Le véritable saut intellectuel arrive lorsqu’on commence à demander :

Pourquoi le réseau a-t-il été conçu ainsi ?

Puis :

Qu’est-ce que cette architecture optimise ?

Et enfin :

Que se passerait-il si je changeais une de ses hypothèses fondamentales ?

Mon idée d’un réseau local essentiellement L2 et d’un L3 réservé à l’interconnexion n’est probablement pas une solution universelle.

Elle rencontre rapidement des problèmes d’échelle, de hiérarchisation, de mobilité et de routage.

Mais elle m’a permis de comprendre quelque chose de beaucoup plus important :

une architecture réseau n’est pas une collection arbitraire de protocoles.

Chaque couche existe parce qu’elle résout un problème particulier.

Et lorsqu’on commence à comprendre ces problèmes plutôt qu’à mémoriser leurs solutions, on cesse progressivement d’être quelqu’un qui « apprend le réseau ».

On commence à raisonner comme quelqu’un qui conçoit des réseaux.
